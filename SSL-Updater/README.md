# SSL-Updater -- Automated Let's Encrypt Certificate Renewal

Automates Let's Encrypt certificate issuance and renewal for **Azure AD App Proxy** applications, **App Service Plan** web apps, and **Application Gateway** listeners. Designed to run as a scheduled **Azure Automation Runbook** using a system-assigned Managed Identity -- no interactive logins or stored credentials in the runbook itself.

## What This Does

On each run the script:

1. Authenticates to Azure and Microsoft Graph using the Automation Account's Managed Identity.
2. Acquires a blob-level write lock to prevent concurrent runs (from other runbooks or schedules that share the same Posh-ACME profile).
3. Downloads the persisted [Posh-ACME](https://github.com/rmbolger/Posh-ACME) configuration from an Azure Storage blob.
4. Enumerates App Proxy applications via Microsoft Graph Beta, checks each certificate's expiry, and renews those within the renewal window using DNS-based ACME validation.
5. Optionally processes **App Service Plan** web apps and **Application Gateway** listeners for the same renewal logic.
6. Uploads the updated Posh-ACME configuration back to storage and releases the lock.
7. Cleans up all temporary private key material from the worker.

### Rate-Limit Awareness

Let's Encrypt enforces a limit of ~50 certificates per registered domain per week. To avoid hitting this, the script uses a randomized renewal window: certificates are not all renewed on the same day but instead probabilistically selected based on how close they are to expiry. The `daysLeftWhenRenewing` parameter controls this threshold.

## Prerequisites

### 1. Azure Automation Account

Create an Azure Automation Account with a **system-assigned Managed Identity** enabled.

```bash
az automation account create \
  --name <automation-account> \
  --resource-group <rg> \
  --location <location>

az automation account identity assign \
  --name <automation-account> \
  --resource-group <rg>
```

### 2. Managed Identity Permissions

The Automation Account's Managed Identity needs the following permissions:

| Scope | Role / Permission | Why |
|-------|-------------------|-----|
| Key Vault | **Key Vault Secrets User** | Read PFX password, DNS API credentials |
| Key Vault | **Key Vault Certificates Officer** | Import renewed PFX certificates (if `SaveCertificateToKeyVault` is enabled) |
| Storage Account | **Storage Blob Data Contributor** | Read/write Posh-ACME config ZIP and lock blobs |
| Microsoft Graph | **Application.ReadWrite.All** (application permission) | Read App Proxy configurations and update certificates via `Update-MgBetaApplication` |
| App Service (optional) | **Website Contributor** on relevant resource groups | Manage App Service certificates (if `-WorkOnAppServicePlans` is used) |
| Application Gateway (optional) | **Contributor** on the gateway resource groups | Update SSL certificates on listeners (if `-WorkOnApplicationGateways` is used) |

Grant the Graph application permission via PowerShell:

```powershell
$mi = Get-MgServicePrincipal -Filter "displayName eq '<automation-account>'"
$graph = Get-MgServicePrincipal -Filter "appId eq '00000003-0000-0000-c000-000000000000'"
$role = $graph.AppRoles | Where-Object { $_.Value -eq 'Application.ReadWrite.All' }
New-MgServicePrincipalAppRoleAssignment -ServicePrincipalId $mi.Id `
    -PrincipalId $mi.Id -ResourceId $graph.Id -AppRoleId $role.Id
```

### 3. Azure Key Vault

Create a Key Vault and populate it with:

| Secret Name | Contents |
|-------------|----------|
| *(your PFX password secret)* | Password used to encrypt PFX files generated by Posh-ACME |
| *(your DNS API key secret)* | API key / username for your DNS provider |
| *(your DNS API secret)* | API secret / password for your DNS provider |

> **Important:** Enable template deployment if you also use this vault for Bicep deployments. For this script, only RBAC access (via Managed Identity) is required.

### 4. Azure Storage Account

Create a storage account and container to hold the Posh-ACME configuration:

```bash
az storage account create --name <storage-account> --resource-group <rg> --sku Standard_LRS
az storage container create --name <container-name> --account-name <storage-account>
```

The script persists its ACME account, orders, and certificates as a ZIP blob (`posh-acme.zip`) in this container. A lock blob (`posh-acme.settings.lock`) prevents concurrent runs.

### 5. PowerShell Modules

The following modules must be available in the Automation Account (install via **Modules** > **Browse gallery** in the portal, or use `az automation module create`):

| Module | Version | Purpose |
|--------|---------|---------|
| **Az.Accounts** | Latest | `Connect-AzAccount -Identity` |
| **Az.KeyVault** | Latest | Read secrets, import certificates |
| **Az.Storage** | Latest | Blob read/write for config and lock |
| **Microsoft.Graph.Beta.Applications** | Latest | Read/update App Proxy certificate config |
| **Posh-ACME** | 4.x+ | ACME client for Let's Encrypt |
| **Az.Websites** | Latest | Only if using `-WorkOnAppServicePlans` |
| **Az.Network** | Latest | Only if using `-WorkOnApplicationGateways` |

### 6. DNS Provider

You need API credentials for one of the supported DNS providers. The script uses these to create DNS TXT records for ACME domain validation.

**Supported providers:** Aliyun, All-Inkl, Cloudflare, Combell, Constellix, DnsMadeEasy, DNSPod, DNSimple, DigitalOcean, deSEC, DomainOffensive, Domeneshop, GoDaddy, Rackspace

The credentials are stored as secrets in Key Vault and referenced by name via the `DnsApiKeyName` and `DnsApiSecretName` parameters.

## Usage

### Azure Automation Runbook

Import the script as a PowerShell runbook:

```bash
az automation runbook create \
  --automation-account-name <automation-account> \
  --resource-group <rg> \
  --name SSL-Update-AzureADApps \
  --type PowerShell \
  --content @SSL_Update_AzureADApps.ps1

az automation runbook publish \
  --automation-account-name <automation-account> \
  --resource-group <rg> \
  --name SSL-Update-AzureADApps
```

Create a schedule (e.g., daily):

```bash
az automation schedule create \
  --automation-account-name <automation-account> \
  --resource-group <rg> \
  --name daily-ssl-renewal \
  --frequency Day \
  --interval 1 \
  --start-time "2025-01-01T02:00:00Z"
```

Link the schedule to the runbook with parameters:

```bash
az automation job-schedule create \
  --automation-account-name <automation-account> \
  --resource-group <rg> \
  --runbook-name SSL-Update-AzureADApps \
  --schedule-name daily-ssl-renewal \
  --parameters '{
    "storageResourceGroup": "rg-automation",
    "storageAccountName": "stacmeconfig",
    "storageContainer": "posh-acme",
    "keyVault": "kv-certs",
    "pfxSecretName": "acme-pfx-password",
    "DnsApiKeyName": "dns-api-key",
    "DnsApiSecretName": "dns-api-secret",
    "DnsProvider": "DnsMadeEasy",
    "CertContact": "certs@contoso.com"
  }'
```

### Dry Run

Use the `-DryRun` switch to see which certificates would be renewed without making any changes:

```powershell
.\SSL_Update_AzureADApps.ps1 `
  -storageResourceGroup 'rg-automation' `
  -storageAccountName 'stacmeconfig' `
  -storageContainer 'posh-acme' `
  -keyVault 'kv-certs' `
  -pfxSecretName 'acme-pfx-password' `
  -DnsApiKeyName 'dns-api-key' `
  -DnsApiSecretName 'dns-api-secret' `
  -CertContact 'certs@contoso.com' `
  -DryRun
```

In dry-run mode the script still connects to Azure and Graph (read-only enumeration), but skips certificate generation, application, Key Vault upload, and Posh-ACME config persistence.

## Parameter Reference

### Required Parameters

| Parameter | Type | Description |
|-----------|------|-------------|
| `storageResourceGroup` | string | Resource group containing the storage account |
| `storageAccountName` | string | Storage account holding the Posh-ACME config blob |
| `storageContainer` | string | Blob container name |
| `keyVault` | string | Key Vault name for secrets and certificate storage |
| `pfxSecretName` | string | Key Vault secret name for the PFX encryption password |
| `DnsApiKeyName` | string | Key Vault secret name for the DNS API key/username |
| `DnsApiSecretName` | string | Key Vault secret name for the DNS API secret/password |

### Optional Parameters

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `DnsProvider` | string | `DNSMadeEasy` | DNS provider for ACME validation |
| `DnsAlias` | string | `''` | CNAME alias for DNS validation (when the target domain's DNS isn't managed by your API) |
| `DnsSleep` | int | `120` | Seconds to wait for DNS propagation before ACME validation |
| `ValidationTimeout` | int | `60` | Seconds to wait for ACME server validation response |
| `RegExDontUpdateTheseCerts` | string | `'^$'` | Regex pattern matching certificate subjects to skip |
| `daysLeftWhenRenewing` | int | `16` | Renewal probability threshold (days before expiry) |
| `CertContact` | string | | Email for the ACME account (receives expiry notices) |
| `AcmeCertServer` | string | `LE_PROD` | `LE_PROD` or `LE_STAGE` (use staging for testing) |
| `SaveCertificateToKeyVault` | bool | `$true` | Import renewed PFX into Key Vault after applying |
| `WorkOnApplicationGateways` | switch | `$false` | Also process Application Gateway listener certificates |
| `WorkOnAppServicePlans` | switch | `$false` | Also process App Service Plan web app certificates |
| `DryRun` | switch | `$false` | Log what would be renewed without making changes |

## Concurrency Control

The script uses a blob-based lock file (`posh-acme.settings.lock`) to prevent concurrent runs from corrupting the shared Posh-ACME configuration:

- Before starting, the script checks for an existing lock blob.
- If locked, it retries up to 3 times with random back-off (30-120 seconds).
- Lock files older than 20 hours are force-released (the stale blob is archived with a timestamp for forensics).
- On completion (or error), the lock is released.

> **Note:** Other scripts in the organization may use this same lock file for coordinating access to the shared Posh-ACME profile. Do not change the lock blob name without updating those scripts as well.

## Security Design

- **No hardcoded secrets.** All credentials come from Azure Key Vault at runtime, referenced by secret name (not value).
- **SecureString throughout.** DNS API secrets and PFX passwords remain as `SecureString` objects. The only plaintext conversion is for the Microsoft Graph API call (`Update-MgBetaApplication`) which requires a plaintext PFX password in the request body -- the BSTR is zeroed immediately after conversion and the variable is nulled after use.
- **Private key cleanup.** After each certificate is applied, all temporary key material (`.key`, `.pfx`, `.cer`, `.csr`, `.bak`, `pluginargs.json`) is deleted from the worker filesystem.
- **Managed Identity authentication.** No service principal secrets or certificates are stored in the runbook. The Automation Account's system-assigned Managed Identity handles all authentication.

## Troubleshooting

### Check Runbook Output

In the Azure portal, navigate to **Automation Account** > **Jobs** > select the run > **Output** tab.

### Common Issues

| Symptom | Likely Cause | Fix |
|---------|-------------|-----|
| "Cannot get write access to config profile" | Another run is in progress or a stale lock exists | Wait for the other run to finish, or check if the lock is stale (>20h old -- it will be auto-cleaned on next run) |
| Key Vault access denied | Managed Identity missing `Key Vault Secrets User` role | Grant the role on the Key Vault |
| Graph API 403 | Managed Identity missing `Application.ReadWrite.All` | Grant the Graph application permission (see Prerequisites) |
| DNS validation fails | DNS API credentials invalid, or DNS propagation too slow | Verify Key Vault secrets; increase `DnsSleep` parameter |
| "No posh-acme configuration found" | First run (expected) or storage blob missing | Normal on first run -- a new ACME account will be created |
